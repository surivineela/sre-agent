## Enovy issue Diagnosis Process Workflow

### Step 0: Parameter Collection
Collect the following inputs:
- `fromDate` (Required)
- `toDate` (Required)
- `region` (Required) — convert to lowercase and remove spaces before tool use (e.g., `"francecentral"`)
- `containerAppName` (Required)
- `resourceGroupName` (Required)
- `subscriptionId` (Required) 
If any of these parameters are missing, use the `AskUserForInput` tool to ask the user for the missing parameters.

### Step 1: Use the `GetContainerAppManagedCluster` tool to fetch the Managed Cluster name of the Container App.
- If the tool returns the managedClusterName, use the `NotifyUser` tool to notify the user with the Managed Cluster name in the format: `"Managed Cluster name found: [managedClusterName]"`
- If the tool does not return the managedClusterName, use the `NotifyUser` tool to notify the user: `"Error fetching Managed Cluster name: [error message]"`. Then, use the `AskUserForInput` tool to ask the user for the Managed Cluster name.
Do not procced with the workflow if the Managed Cluster name is not found. You will need to use the `managedClusterName` as the input parameter in the next steps.

### Step 2: Retrieve and Analyze Envoy Access Logs
- Step 2.1: Verify the `fromDate` and `toDate` parameters.
  If the time range between `fromDate` and `toDate` is more than 2 hours, use the `AskUserForInput` tool to notify the user: `"The time range is too large. Please narrow it down to 2 hours or less."`, and ask for a new time range. Continue the workflow with the new time range, if provided.
- Step 2.2: Use the `GetEnvoyAccessLogs` tool to fetch Envoy Access Logs.
  - If the tool returns no access logs, it indicates there are potential issues with the Envoy component or load balancer. You must:
    1. Use the `NotifyUser` tool to notify the user: `"No Envoy Access Logs found for the specified time range. I am checking the Envoy component healthy status."`
    2. Go to the **Step 3** to continue the investigation.
  - If the tool returns access logs, it indicatest that the Envoy component is working properly. You must:
    1. Summarize the logs and use the `NotifyUser` tool to notify the user: `"Envoy Access Logs found: [summary of the logs]"`
         - For those requests with 'Status' in 5xx range, provide a detailed description of the access logs, including FirstSeen, LastSeen, RequestDuration, Count, Authority, Method, Path, Protocol, Status, ResponseCodeDetails, UpstreamHost.
         - For those requests with 'Status' smaller than 5xx, provide a brief description of the access logs, including FirstSeen, LastSeen, Count and Status.
    2. Go to **Step 2.3** to analyze the access logs.
- Step 2.3: Analyze the access logs:
  Focus Areas: `ResponseCodeDetails`, `UpstreamHost` and `Status`.
  - If `ResponseCodeDetails` contains the keyword `upstream`, this indicates that the Envoy component successfully forwarded the request to the upstream component. Next, examine the `UpstreamHost` field:
     - If the port is '4045':
       **Description and Suggestion**: `"Some requests were handled by the 'Activator' component, as indicated by the upstream host port 4045. This suggests that the customer's application pod did not start in time. Please verify the health and readiness status of the customer's application pod."`
     - If the port is not '4045', this indicates that the Envoy component successfully forwarded the request to the customer's application pod, and the request was handled by that pod. Next, examine the `Status` field:
       - If the response `Status` is in the 5xx range:
         **Description and Suggestion**: `"Some requests were handled by the customer's application pod but returned an HTTP [Status], indicating that the application failed to process them successfully. Please advise the customer to review their application logs for further investigation."`
       - If the response `Status` is not in the 5xx range:
         **Description and Suggestion**: `"Some requests were handled by the customer's application pod and returned an HTTP [Status], indicating that the request was successfully processed by the application."`
  - If `ResponseCodeDetails` contains the keyword `downstream`, it indicates a client-side issue.
    **Description and Suggestion**: `"Some requests returned [ResponseCodeDetails], which suggests a downstream issue—commonly associated with client-side problems. Please advise the customer to review their client logs for further investigation."
  - If `ResponseCodeDetails` does not contain upstream or downstream, it indicates an issue that may not be directly related to either the client or upstream components.
    **Description and Suggestion**: `"Some requests returned [ResponseCodeDetails], which may indicate a problem unrelated to the client or upstream services. Proceeding with further investigation into potential issues within the container application or underlying network infrastructure."`
- Step 2.4: Used the "NotifyUser" tool to notify the user in a **well-formatted markdown** including comprehensive descriptions and suggestions of the access log analysis result.
- Step 2.5: Go to **Step 4** to continue the investigation.

### Step 3: Check Envoy Component Healthy Status
If you retrieved Envoy Access Logs in **Step 2.2**, you can skip this step and go to **Step 4**.
- Step 3.1: Use the `GetEnvoyPodLogs` tool to fetch Envoy Pod Logs.
  Only when you retrieved the `region`,`fromDate`, `toDate`, and `managedClusterName` parameters, you can execute the `GetEnvoyPodLogs` tool.
  - If the `GetEnvoyPodLogs` tool returns no logs, use the `NotifyUser` tool to notify the user: `"No Envoy Pod Logs found for the specified time range."`
  - If envoy pod logs are found, summary the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Envoy Pod Logs found: [summary of the logs]"`
- Step 3.2: Use the `GetEnvoyControllerLogs` tool to fetch Envoy Controller Logs.
  - You should first check if the tool returns any error message. If there is, use the `NotifyUser` tool to notify the user: `"Envoy Controller Errors found: [summary of the errors]"`
  - Summarize the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Envoy Controller Logs summary: [summary of the logs]"`
- Step 3.3: Use the `GetEnvoyPodStatus` tools to fetch Envoy Pod Status and Envoy Controller Pod Status
  Summarize the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Envoy Pods Status summary: [summary of the logs]"`

### Step 4: Check Container App and Customer App Pod Healthy Status
- Step 4.1: Use the `GetContainerAppStatus` tools to fetch  the Container App Status.
  Summarize the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Container App Status summary: [summary of the logs]"`
- Step 4.2: Use the `GetCustomerAppPodStatus` tools to fetch Customer Application Pod Status.
  Summarize the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Customer Application Pods Status summary: [summary of the logs]"`

### Step 5: Check Networking Events
- Step 5.1: Use the `GetSwiftNetworkingEvents` tool to fetch Swift Networking Events.
  - You should first check if the tool returns any error message. If there is, use the `NotifyUser` tool to notify the user: `"Swift Networking Errors found: [summary of the errors]"`
  - Summarize the log and use the `NotifyUser` tool to notify the user with the summary of the logs in the format: `"Swift Networking Events summary: [summary of the logs]"`
  - If the tool returns no logs, use the `NotifyUser` tool to notify the user: `"No Swift Networking Events found for the specified time range."`
