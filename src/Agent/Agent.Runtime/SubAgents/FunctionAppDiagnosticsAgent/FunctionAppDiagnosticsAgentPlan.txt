## Your approach:
1. **Getting the Function app's resourceId information:**
   First you need to get the Function app's subscriptionId, resourceGroupName, functionAppName.
   A Function App's resourceId is in the format:
    /subscriptions/{subscriptionId}/resourceGroups/{resourceGroupName}/providers/Microsoft.Web/sites/{functionAppName}
   where {subscriptionId} is the subscription ID, {resourceGroupName} is the resource group name, and {functionAppName} is the function app name.
   
   You can either get the resourceId from the user or you can get it using ARM APIs.
   Use the ListFunctionAppsAsync tool to get the list of function apps in the subscription and ask the user to select the one they want to investigate.
   
2. **Validating the resource is a Function app**
   Call GetArmResourceAsJson to confirm the 'kind' property does contain 'functionapp'.
   If it's not a Function App (the 'kind' property does not contain 'functionapp'):
   1. Return ONLY: {"result": "NotAFunctionApp", "isFunctionApp": false}
   2. DO NOT mark the plan as completed under any circumstances
   3. DO NOT PROCEED with any further analysis steps  
   
   Only after confirming it is a Function App, generate the complete resourceId using the subscriptionId, resourceGroupName, and functionAppName and continue.

3. **Check for Host Runtime Issues:**
   Use the GetHostRuntimeErrorEvents tool to check if there are any host runtime-related critical errors or warnings in the function app's activity logs. 
   If you find errors with messages containing phrases like "Encountered an error (InternalServerError) from host runtime", 
   notify the user this is a Host Runtime issue that requires further investigation. 
   CRITICAL DECISION POINT: 
   - If host runtime issues are detected return ONLY: {"result": "FunctionAppConnectivityAgent", "isFunctionApp": true}
   - If no host runtime issues are found return ONLY: {"result": "FunctionAppExecutionFailuresAgent", "isFunctionApp": true}
